# 版本管理

- 固定程序版本使用 Git Tag 和 GitHub Release；例如 `relay-v0.1.0-test1`、`exit-v0.2.0-test1`；总控预留 `controller-v版本号`。每个版本保留独立源码和安装包，发布后不移动标签、不替换程序包。
- `main` 是继续开发的分支；`history/0.1.0-test1` 是第一版的归档分支，供查看历史代码。下载固定版本请使用标签和 Release，而不是会变化的 main。
- 测试版本号为 `主版本.次版本.修订号-test序号`，GitHub 标为 Pre-release，安装菜单显示“（测试版）”。正式版没有 test 后缀和测试版注释。示例 0.4.2 / 0.5.0 尚未发布，不会出现在安装菜单。
- 同一基础版本按 test1、test2、…、正式版排列。正式安装只自动检查正式版本，测试安装可检查更新的测试版和正式版；都不会自动降级。
- 首次安装先选中转／出口，再列出该角色真实已发布且有完整校验信息的程序包。无人值守安装用 `bash bootstrap.sh --version v0.2.0-test1 --role relay`（出口端用 exit）。两版安装器均支持角色参数，历史版仅回补安装兼容和降级保护。
- 安装器不能覆盖已安装的其他版本，不能将新版数据库交给旧版。需要体验旧版时请使用空白测试服务器；不要直接覆盖或导入新版配置。
- 原先已发布的 `v0.2.0` 保留标签和程序包，避免破坏旧下载地址；该 Release 标记为“安装入口”，不再作为安装菜单里的正式版本。仅其中的 bootstrap.sh 与校验附件持续更新，保证旧的一行安装命令仍能显示新版菜单。固定版本程序包不随之变化。
- 0.1.0-test1 来源是第一版最后一次修正的历史代码，仅补安装器兼容和降级保护；0.2.0-test1 是简化引导、配对和细化用户管理的新版本。两版均是测试版，不声称已经完成生产验收。

发布流程：更新 package.json 和 lock 中版本 → 检查与回归 → 推送 main → Actions 构建、校验并创建对应固定 Release。已存在版本只保留，不覆盖；要发布修正必须提升版本号。历史发布只允许配置中固定的提交。

## 仓库导航与职责

首页给出中转、出口、总控三个入口；apps/relay、apps/exit、apps/controller 的说明分别维护对应版本表。GitHub Release 名称前缀固定为【中转端】、【出口端】、【总控端】，标签分别使用 relay-、exit-、controller-。例如只查看中转端 0.2.0-test1：打开 relay-v0.2.0-test1 的 Release 或源码标签。

当前中转／出口复用根目录 src 中的引擎和 Web 组件，通过角色决定页面及权限，避免复制代码导致修复不同步。apps 下是清晰的产品入口；未来总控有独立实现时再放入 apps/controller。只建立入口不代表总控已经开发完成。
